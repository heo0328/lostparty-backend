- **최신 통합:** 진단·인계 문서 `48bf88c` 게시 후 사용자 승인으로 [PR30](https://github.com/heo0328/lostparty-backend/pull/30)·병합 `fc6c06a`를 dev/main에 원격 반영했다. 그룹 브랜치는 로컬·원격 정리, checkout은 dev다. 미완료 활동 선택 브랜치는 보존한다. 코드/API/서버/DB 추가 변경은 없다.
- **미착수:** 아래 F01~F09 구현·운영 검증 및 F10 잔여 사실 정정. 문서화는 각 대안의 확정이나 모든 개선의 일괄 실행 승인이 아니다. 다음 탭에서 선택한 구간을 실행하며 필요한 정책/계약 결정만 해당 작업에 앞서 받는다.
- **독립 대기:** 그룹 신규 최초 연결·목록/배지의 기기 인수는 #29와 다르다. 문서 협의 완료를 기능 인수 완료로 확대하지 않는다. 기존 그룹 정상 흐름의 완료 근거는 재사용한다.

## 적용 방식 — 전부 한 번에 바꾸지 않는다

| 작업 성격 | 처리 방식 | 대표 항목 |
|---|---|---|
| Backend 사실 정정 | 코드/기록과 대조하여 직접 정정, 공통 정책을 바꾸지 않음 | F10의 환경·검증 안내 |
| Backend 내부 개선 | 외부 계약/데이터 정책을 보존하는 작은 구간으로 구현·검증 | F01, F03 로그 내부 개선 |
| 사용자 정책 결정 | 베타 지원 범위·운영 목표를 먼저 결정. 네이티브 합의로 대신하지 않음 | F04·F06 |
| 네이티브 협의 필요 | 기존 Issue/계약과 차이만 논의하고 Backend만/네이티브만/양측 변경 여부를 판정 | F03 오류 응답, F06 지원/안내 |
| 합의 후 적용 | 의존 순서에 따라 구현·검증·게시·인계. 상대 측 작업이 필요한 경우에만 요청 | 계약 변경 구간 |

협의 중에도 독립적인 Backend 수정은 진행할 수 있다. 문서 수정이 작다는 이유로 모든 문서를 먼저 정리하지 않으며, 모든 항목을 #29로 확장하지 않는다. 새 협업 주제가 실제로 필요할 때 기존 관련 Issue 범위를 확인하고 별도 추적 여부를 판단한다. 이번 기록에서는 Issue/브랜치를 만들지 않는다.

## 권장 실제 실행 순서

기간은 1인 개발·기존 구조 재사용·안전한 검증 환경 이용 가능 전제의 개발일 추정이다. 대기/운영 승인·실패 수정 시간은 별도이며 합산 출시 일정으로 사용하지 않는다.

| 순서·작업 구간 | 관련 항목 / 목적 | 선행 조건 | 완료 조건 | 미루는 영향 / 상태 |
|---|---|---|---|---|
| 0. 범위 확인 병행 | F05/F06/F10: 베타 지원/후보 기준과 오래된 안내 구분 | 사용자 지원 의도·기존 Issue 최신 확인 | 지원/제한/제외와 검증 목록 초안, 명백한 사실 정정 | 뒤늦은 범위 변경은 재작업. F01 착수를 막지 않음 / 미착수 |
| 1. 삭제 등록정보 정리 진행 보장 | F01: 가장 명확한 내부 결함부터 수정 | cleanup/모델/보존 계약 재확인, 격리 DB | 200개 초과·중단/재시도·보존 회귀 통과 | 미정리 자료가 누적될 수 있음 / 첫 구현 추천, 0.5~1.5일 |
| 2. 공개 접속·인증 제한 | F02: 배포 경로에서 사용자별 제한 보장 | 프록시/직접접근 정책 | 사용자 분리·위조 전달 헤더·로그인 검증 | 공개 후 정상 로그인 차단 위험 / 미착수, 1~2일 |
| 3. 장애 원인 추적 | F03: 개인정보 없이 분류·상관관계 확보 | 내부 로그와 외부 응답 변경 분리, 응답 변경 시 협의 | 일반/DB/응답검증 예외와 비노출 회귀 | 장애 재현 자료를 놓칠 수 있음 / 미착수, 1~2일 |
| 4. 최소 운영·복구 | F04: 실패 발견과 복구 가능성 확보 | 운영 호스트·담당·허용 손실/복구시간 | 격리 복원 및 실패 알림·대응 절차 검증 | 사용자 자료 복구 불능 가능 / 미착수, 2~4일 |
| 5. 출시 후보 검증 | F05/F06/F07: 지원 범위·동시성·운영 인수 판단 | 위 수정 반영 후보, 지원 정책·부하 목표 | 고정 SHA/프로필의 필수 회귀·계약·부하 결과, 잔여 위험 판단 | 선택 시험을 전체 준비 완료로 오인 / 미착수, 목록1~2일+측정1~2일+실행/보완 |

0과1은 병행 가능한 논의/구현이며, 2~4도 환경 의존성에 따라 순서를 조절할 수 있다. 단, 공개 베타 판정5는 필요한 결과를 모은 후 수행한다. 각 구간의 목적·완료 조건으로 관련 코드/시험/문서/협업을 묶고 파일 종류마다 별도 브랜치를 만들지 않는다.

## 첫 구현 구간 — F01

**목적:** 삭제 후 유예기간을 지난 등록정보가 회차별 배치에서 빠짐없이 마스킹되도록 한다. 실제 사용자 자료를 직접 정리하는 작업이 아니라 코드와 격리 시험의 보완이다.

- 포함: `app/game_accounts/cleanup.py`의 Registration 대상 선택 조건/순서, 관련 모델 nullable/JSON 비교 의미 확인, 450개 이상/부분 마스킹/기존 완료 행/활성·유예 행의 격리 회귀, 반복·중단/rollback·동시 실행, 데이터/이력 보존 확인.
- 추천: 미처리 조건+결정적 순서를 우선 검토. 최소 수정으로 안정적인 완료 판별이 불가능할 때만 완료시각 컬럼 대안과 migration 필요성을 설명한다.
- 제외: 보존기간 변경·물리 삭제·회원 탈퇴·전역 잠금 분리·다른 cleanup 전면 재작성·provider 호출·실DB 마스킹·배포·소유권/네이티브 API 변경.
- 산출물: 작은 코드 수정, 재현/회귀 시험, 실제 실행 결과와 미실행 조건, 상세 진단 원본을 연결한 완료 이력. 계약 변경이 없으면 네이티브 구현/기기 재시험 요청은 불필요하다.
- 먼저 필요한 사용자 결정: 현행 마스킹 의미·보존 정책을 유지하는 추천안에는 새 제품 정책 결정이 없다. 보존기간/삭제 정책을 바꾸려는 경우만 별도 결정이 필요하다. 검증 환경이 실DB만 가능하면 실행하지 않고 격리 환경 조건을 확보한다.
- 완료 후: 이 계획 F01 상태/검증 근거와 NEXT_WORK를 갱신하고, 해당 구현 구간을 묶어 commit/push. 서버 반영은 별도 승인 범위다.

## 다른 탭에서 재개하는 방법

1. AGENTS → 협업 규칙 → NEXT_WORK → AI_CONTEXT → 이 계획/진단의 F01 및 관련 보존 계약 순서로 읽는다.
2. `git status --short`, 현재 브랜치/HEAD·원격 차이를 확인한다. 진단 인계는 `48bf88c`에 보존하고 PR30으로 dev/main 통합 완료했다. F01은 최신 dev에서 베타 개선 목적 브랜치를 만들어 진행한다. 다른 탭에서 이미 생긴 변경을 보존한다. 문서가 쓰인 시점과 현재 Git 상태를 혼동하지 않는다.
3. F01 구현을 시작한다는 작업 범위를 확인하고 cleanup/테스트 설정을 읽는다. 직접 pytest를 실행하지 말고 격리 runner/compose.test의 DB·키·외부 호출 조건을 확인한다. package/image 준비와 실행 환경이 허용되는 범위인지 확인한다.
4. 기능과 무관한 #29 재회신·이미 인수한 그룹 시험을 반복하지 않는다. F02~F06 정책 질문은 실제 의존 작업 전에만 구체 선택지로 묻는다.

사용 가능한 재개 요청 예: “NEXT_WORK와 backend-improvement-plan을 읽고, F01 삭제 등록정보 정리 배치의 진행 보장 구간부터 구현·격리 검증해 주세요. 기존 보존 정책과 API는 유지하고 실제 서버·데이터는 변경하지 마세요.”
