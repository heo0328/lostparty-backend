# Backend 오픈 베타 전 종합 진단 — 2026-10-30

## 문서 성격과 종합 판단

이 문서는 이번 대화에서 수행한 읽기 전용 조사 결과의 영구 원본이다. 진단 기준은 `feat/group-management`의 업무 구현 `6dac5ab2cc67e197979e7188a9c97ce2c27fb548` 및 후행 문서 상태(기록 시작 HEAD `6b3728c`)다. 후속 실행·상태는 [개선 계획](../../project/backend-improvement-plan.md)에서 관리한다. 조사 기록은 확정 계약이나 전체 개선 착수 승인이 아니다. 이번 기록 작업은 코드·API·DB·서버를 바꾸지 않는다.

FastAPI/Pydantic·동기 SQLAlchemy·Alembic·PostgreSQL 기반 모듈형 단일 서비스 구조는 현재 개인 개발 규모에 합리적이다. 세션 복구와 중복 명령 처리, 쓰기 시 권한 재확인, 트랜잭션 원자성, 외부 공급자 호출 제한, 개인정보를 제한하는 로그, 격리 검증 도구는 유지할 가치가 있다. 전체 재작성보다 실패 경로·운영 준비를 좁혀 보완하는 것이 빠른 베타에 유리하다.

사용자 추정 기능 구현률 80%는 출시 준비율이 아니다. 정리 작업의 진행 보장, 공개 환경의 인증 제한 설정, 장애 원인 추적·복구, 지원할 소유권 흐름과 출시 후보 검증 범위를 먼저 정리해야 한다. 현재 근거만으로 공개 베타 준비 완료를 선언할 수 없다. 성능 저하나 운영 장애 발생을 확인한 것은 아니다.

### F01 — 삭제 등록정보 정리 배치의 진행 보장 부재

- **판정/범위:** 확인된 문제. `app/game_accounts/cleanup.py:25`의 Registration 마스킹 배치.
- **근거:** deleted_at이 24시간 지난 행을 최대200개 선택하고 preview/lookup_name/label을 비우지만, 완료 행 제외 조건·완료 표식·진행 커서가 없다. 처리된 행도 다음 선택 대상이다. `tests/test_game_accounts.py:389` 부근의 보존 시험은 Verification 중심이며 200개 초과 등록정보 진행을 보호하지 않는다.
- **영향/조건:** 대상이 200개를 넘으면 같은 행을 반복 선택해 다른 행의 마스킹이 지연될 수 있다. 실제 운영 누적/발생은 미확인이나 진행 보장이 없는 구조는 확인했다.
- **배경:** 작은 배치와 SKIP LOCKED 사용은 확인했다. 잠금 시간을 줄이려는 선택이라는 설명은 추정이다.
- **선택지:** 현상 유지는 비용이 없지만 진행을 보장하지 못한다. 미처리 조건과 결정적 순서 추가는 변경이 작지만 부분 마스킹/NULL 의미를 정확히 다뤄야 한다. 완료시각 컬럼은 명시적이나 migration과 기존 자료 보정이 필요하다.
- **추천/시점:** 베타 전에 미처리 조건+순서로 최소 수정. 기존 보존 기간·식별자/FK·이력은 유지하고 물리 삭제로 바꾸지 않는다.
- **규모/전환:** 0.5~1.5개발일, 현행 마스킹 의미를 재사용하고 격리 DB 사용 가능하다는 전제. 모든 필드가 일부만 정리된 상태와 동시 실행을 선행 확인한다.
- **완료 기준:** 450개 이상을 여러 회차 처리해 모두 마스킹됨, 기존 마스킹 행이 미처리 행을 막지 않음, 활성/유예 행과 이력 보존, 재실행·중단/rollback·동시 실행 검증.
- **확신:** 구조 높음, 실제 장애 발생 여부 미확인.

### F02 — 공개 프록시 구성과 로그인 제한 키의 정합성

- **판정/범위:** 추가 확인 필요. 프록시 뒤 인증 rate limit의 설정 위험.
- **근거:** `app/auth/router.py:11`은 request.client.host 기반 제한(Google10/min, challenge30/min, refresh300/min)을 사용한다. `compose.two-cycle.yaml:18` 및 Dockerfile은 `--no-proxy-headers`를 사용한다.
- **영향/조건:** 일반 역방향 프록시 뒤에서 원본 주소 전달이 반영되지 않으면 여러 사용자가 프록시 IP 하나의 제한을 공유할 수 있다. 공개 토폴로지/현재 장애는 미확인이다.
- **배경:** 단일 프로세스와 임의 전달 헤더를 신뢰하지 않는 의도는 주석/설정에 드러난다. 그 안전장치는 보존해야 한다.
- **선택지:** edge에서 제한하면 앱 설정이 단순하나 정책이 두 곳에 분산될 수 있다. 신뢰 프록시만 전달 헤더를 허용하면 앱 제한을 유지할 수 있으나 우회 경로 차단이 필요하다. 무조건 모든 XFF 신뢰는 제외한다.
- **추천/시점:** 공개 베타 전 실제 접속 경로를 확정하고 두 방식 중 하나를 검증. 단일 프로세스에서 Redis 도입은 선행 조건이 아니다.
- **규모/전환:** 1~2일, 배포 주소/프록시 접근 가능 전제. 원본 IP 오인·스푸핑·직접 backend 접근 위험을 점검한다.
- **완료 기준:** 서로 다른 사용자 분리, 같은 사용자 제한, 위조 XFF 거부, backend 직접 접근 통제, HTTPS 로그인/refresh 확인.
- **확신/출처:** 설정 사실 높음, 배포 영향 조건부. [Uvicorn 공식 설정](https://uvicorn.dev/settings/)의 proxy headers/forwarded allow IPs 참조. 구현 시 잠금 버전의 지원 옵션을 확인한다.

- **선택지:** 수동 확인은 비용이 낮지만 누락 위험, 최소 자동 백업/상태 알림은 소규모에 적합, 대규모 관측 플랫폼은 비용/설정 부담이 크다.
- **추천/시점:** 베타 전 단일 서버에 맞는 백업·키 안전 보관·복원 연습·worker/백업/디스크 실패 알림과 짧은 대응 절차를 준비한다.

- **확신:** 저장소의 근거 공백 높음, 실제 인프라 부재 여부 미확인.

### F05 — 출시 후보를 승인할 검증 묶음 미정

- **판정/범위:** 추가 확인 필요. 출시 검증의 선택과 완료 기준.
- **근거:** `scripts/isolated_checks.py:14` 기본 선택은 legacy7파일/two-cycle14파일, all94파일이다. 최신 그룹 시험은 기본 two-cycle 전체에 자동 포함되지 않는다(선택/all 실행 가능). 기존 선택49시나리오는 전체 저장소 동일 HEAD 일괄 검증이 아니다. 저장소에 CI workflow는 없다.
- **영향/조건:** 선택 시험 통과를 전체 출시 준비 통과로 오해하면 핵심 경로 누락을 발견하기 어렵다. 테스트 부족이나 CI 필수 도입을 단정하지 않는다.
- **배경:** 작업별 관련 시험 선택은 개발 속도를 위한 합리적 방식이다. 출시용 별도 합격 범위가 필요하다.
- **선택지:** 매 변경 전수시험은 느리다. 출시 후보에 필수 묶음/제외 사유를 정하면 비용과 근거가 명확하다. CI는 재현성을 높이지만 현재 로컬 격리 도구 재사용 후 도입해도 된다.
- **추천/시점:** 베타 전 후보 SHA·프로필·DB revision을 고정하고 인증/권한/키/그룹/모집/주차/cleanup/계약의 필수 검증과 미포함 사유를 정한다.
- **규모/전환:** 목록·실행기록 정리1~2일+실행/실패 보완 시간. 실제 지원 범위(F06)와 안전한 격리 환경이 전제다.
- **완료 기준:** 같은 후보에 대한 필수 결과와 제외 이유 추적 가능, 실제 서버/기기/합성 결과 구분, 실패 해결 또는 출시 범위 축소 결정.
- **확신:** 시험 선택 구조 높음, 공개 출시 합격 기준은 사용자 결정 필요.

### F06 — 소유권·생명주기 기능의 베타 지원 경계

- **판정/범위:** 추가 확인 필요. 분쟁/퇴역/삭제·이름 재사용의 지원 정책과 실인수.
- **근거:** `app/game_accounts/lifecycle.py:43`의 BindingEvidence는 내부/테스트에서 검증되나 실제 provider의 완전·연속 증거 확보는 미완료이며 retire는 증거를 요구한다. `app/ownership_disputes/worker.py`는 활성 파티 영향 시 PARTY_IMPACT_REVIEW_REQUIRED로 보류한다. [#17](https://github.com/heo0328/lostparty-backend/issues/17)의 증거/삭제/이름 재사용은 미완료. [#15 전체9번째](https://github.com/heo0328/lostparty-backend/issues/15#issuecomment-6263145675)의 UI3항목 수용은 전체24시간 분쟁 인수를 의미하지 않는다.
- **영향/조건:** 필요한 증거가 없을 때 안전하게 중단되지만 사용자가 해결 경로를 얻지 못할 수 있다. 권한 우회 결함을 발견했다는 의미는 아니다.
- **배경:** 증거 없는 소유권/퇴역 처리를 거절하는 보수적 설계는 유지할 가치가 있다.
- **선택지:** 전면 지원은 경험이 좋지만 증거/인수 비용이 크다. 제한 지원+운영 대응은 빠르지만 지원 부담이 있다. 제외는 명확하지만 UI만 숨겨서는 API·기존 pending/ACK가 남는다.
- **추천/시점:** 베타 전 사용자 지원 범위를 결정하고 네이티브와 필요한 계약/안내만 협의한다. 근거 없는 자동 퇴역은 도입하지 않는다.
- **규모/전환:** 범위 결정0.5~1일, 구현/인수2~5일 이상(정책 의존). 기존 pending/ACK·파티 자료 보존과 사용자 다음 행동이 선행 조건이다.
- **완료 기준:** 포함 흐름의 방어/만료/활성 파티·이름변경/404/부분응답 확인 또는 제외 범위의 서버 진입/기존 상태 처리 합의 및 검증.
- **확신:** 증거/인수 공백 높음, 최종 지원 정책 미정.

### F07 — 전역 쓰기 잠금과 worker 처리량

- **판정/범위:** 개선 선택지. 현재 성능 장애는 미확인.
- **근거:** `app/game_accounts/support.py:34` 부근의 쓰기는 전역 advisory lock game-mutations-v1을 사용하며 cleanup도 공유한다. cleanup 일부 삭제는 개수 상한이 없고 `app/raid_rooms/cycle_worker.py:69` 부근은 열린/review 방을 순차 처리한다.
- **영향/조건:** 자료/동시 쓰기가 늘면 정리·주차 작업이 일반 요청 대기시간을 늘릴 수 있다. 실제 부하 수치는 없다.
- **배경:** 초기 도메인 간 무결성 확보를 위한 직렬화는 합리적이며 잠금 제거 시 경쟁 조건을 되살릴 위험이 있다.
- **선택지:** 유지+측정은 저비용, 배치 상한은 처리량/잠금시간 조절에 유리, 엔티티별 잠금은 병렬성 이득 대신 교착/무결성 비용이 크다.
- **추천/시점:** 베타 전 예상 소규모 부하에서 측정, 허용 범위면 유지. 배치 보완/잠금 분리는 운영 근거를 보고 결정한다.
- **규모/전환:** 측정1~2일, 필요한 배치 보완1~3일; 잠금 분리 별도 산정. 예상 사용자/지연 허용치와 경쟁 불변식 확인 필요.
- **완료 기준:** 요청+cleanup+rollover 동시 실행의 잠금 대기·timeout·진행률 측정과 허용치 판단, 자료 불변식 유지.
- **확신:** 구조 높음, 사용자 영향 미확인.

### F08 — 그룹 조회에서 페이지 이전 처리·반복 쿼리

- **판정/범위:** 개선 선택지. 그룹 목록/요약에 한정.
- **근거:** `app/groups/http_service.py:80`은 항목마다 summary를 호출하고 `app/groups/service.py:46`은 캐릭터/계정/멤버/대표/집계 등을 조회한다. ORM 캐시가 일부를 줄여도 모두 제거하지 않는다. `app/groups/display.py:195`의 my_groups는 전체 상세 구성 후 페이지를 자른다. 모집에는 이미 cycle_card_batch 최적화가 있어 전체 코드로 일반화하지 않는다.
- **영향/조건:** 그룹 수/멤버 수 증가 시 불필요한 조회 비용이 커질 수 있다. 현재 한도 내 체감 저하는 미확인이다.
- **배경:** 작은 규모에서 기존 상세 함수를 재사용한 것으로 추정한다.
- **선택지:** 유지가 가장 단순, bulk 조회는 쿼리 수를 줄이지만 snapshot/권한 재확인 필요, 캐시는 무효화 책임을 늘린다.
- **추천/시점:** 관련 그룹 개발 때 쿼리 수/시간을 측정하고 필요하면 bulk 처리. 베타 이후 지연/사용량을 근거로 확장하며 캐시부터 도입하지 않는다.
- **규모/전환:** 측정0.5~1일, 보완1~2일. 페이지/cursor/정렬·권한·현재 상태 의미 보존 필요.
- **완료 기준:** 대표 크기별 쿼리/응답시간 개선 및 동일 응답/권한/페이지 회귀 확인.
- **확신:** 호출 구조 높음, 개선 시급성은 미확인.

### F09 — 공통 처리와 정책 조립 책임의 분산

- **판정/범위:** 개선 선택지. 앱 조립·모집 라우터의 변경 비용.
- **근거:** `app/main.py:89` 부근 앱 구성에 많은 정책/OpenAPI 장식이 섞인다. `app/raid_rooms/cycle_router.py:67` 부근은 경로별 허용 query를 수동 나열한다. cycle_common 경유 연결과 F03의 예외 처리가 중복 책임의 구체 사례다. 단지 파일이 길거나 함수명이 다르다는 이유의 문제 판정은 아니다.
- **영향/조건:** 새 경로를 추가할 때 파라미터/정책/오류 처리 여러 지점을 함께 맞춰야 한다. 모든 도메인에 같은 구조 결함이 있다고 보지는 않는다.
- **배경:** 기본/주차 프로필 호환·복구 계약으로 인한 실제 복잡성도 포함돼 있다.
- **선택지:** 전체 계층 교체는 전환 위험이 크다. 변경 경로부터 타입/공통 오류 처리와 앱 조립·정책을 분리하면 작은 검증 단위로 개선할 수 있다. 단순 유지도 변경 빈도가 낮은 부분에는 합리적이다.
- **추천/시점:** 남은 기능 개발과 함께 해당 경로만 개선. 중복 JSON 키 거부·엄격한 경계값 등 의도적인 계약 검증을 프레임워크 기본값으로 무조건 대체하지 않는다.
- **규모/전환:** 경로 묶음당1~3일, 구체 변경별 재산정. 인증/트랜잭션/rollback·두 프로필 계약 회귀가 선행 조건이다.
- **완료 기준:** 새 경로에서 동일 규칙을 여러 군데 수정할 필요 감소, 계약/오류/권한/복구 결과 보존. 반복 변경이 확인될 때만 기존 경로에 확대.
- **확신:** 구체 중복 높음, 장기 비용 추정 중간.

### F10 — 현재 안내의 오래된 사실과 상태 중복

- **판정/범위:** 확인된 문제, 일부 해결. 공통 문서 운영 합의와 각 문서 사실 정정은 별개다.
- **근거:** environment.md:17~19의 DB0032·178/199, isolated-verification.md:24~26의116/133·177/197·선택8파일은 현재 코드/계약/실행기록과 다르다. logging/기존 architecture review의 ‘현재 checkout’은 과거 feat/raid-recruitment 기준이다. cycle_router.py:1의 미장착 후보 설명과 현재 factory 장착이 다르다. #12/#16 본문 대기는 후행 연결 완료 보고와 대조 필요, #26 전체 완료 판단은 #13 종료 범위와 구분해야 한다.
- **영향/조건:** 새 작업자가 잘못된 revision·시험 범위를 사용하거나 완료된 협업을 재요청할 수 있다. 코드 결함이 이 문구 때문에 생겼다는 인과관계는 입증하지 못했다.
- **배경:** 기능별 개발/반영과 당시 기록이 누적된 사실은 확인. 모든 절차가 과도해서 발생했다는 추론은 하지 않는다.
- **선택지:** 모든 수치를 여러 곳에서 갱신하면 중복 비용 지속, 현재 안내를 단일 실행 근거에 연결하면 유지 비용 감소, 과거 기록을 덮어쓰면 근거 소실.
- **추천/시점:** 지금 가능한 사실 정정과 정책 변경을 분리한다. 고정 과거 자료는 보존, 현재 안내는 기준 날짜/링크 중심으로 보완. 상세 후보는 아래 표를 따른다.
- **규모/전환:** 사실 정정0.5~1일, 남은 원본/중복 정리1~2일. 원문 해시·동결 JSON 보존, 공통 정책 변경은 양측 영향 확인 필요.
- **완료 기준:** 현재 안내/실제 코드/근거 링크 일치, 이미 완료된 대기 제거, 과거 기록 보존 검사와 링크 검사 통과.
- **확신/후속:** 높음. [#29 전체5번째 Backend 대조 완료](https://github.com/heo0328/lostparty-backend/issues/29#issuecomment-6520322169)로 문서 역할·공통 원본·양측 참조 합의는 해결했다. 전체 기술 진단이나 잔여 사실 정정까지 완료한 것은 아니다. 사용자도 문서 협의 최종 확인 완료를 보고했다. 공통 기준을 재협의하지 않는다.

## 유지할 선택과 미확인 사항

모듈형 단일 서비스·동기 ORM·현재 migration·기존 멱등성과 권한/CAS·보수적 증거 요구·격리 테스트를 유지한다. Redis/Celery/Kafka/Kubernetes·전면 비동기화·일괄 repository/DI 교체·새 공통 문서 저장소를 기본 해법으로 삼지 않는다. 다중 인스턴스 필요, 실제 작업 적체, 측정된 지연 또는 반복된 변경 비용이 나타나면 해당 항목만 재검토한다. 특정 라이브러리를 쓰지 않은 사실 자체는 결함이 아니다.

공개 호스트/프록시·예상 동시 사용자·허용 지연, 운영 담당·백업 실체·키 보관/복원 목표, 소유권 기능의 베타 지원 범위, 실제 group 최초 연결 성공과 새 기기 인수, 실제 대량 정리/전역 잠금 부하, 동일 출시 후보의 업무 회귀는 미확인이다. 새 사실이 들어오면 계획의 상태를 갱신하고 이 보고서의 관찰 시점은 보존한다.
