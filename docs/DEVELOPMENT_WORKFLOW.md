# 개발 작업 흐름

## 현재 상태와 초기 방향

현재 기능 상태는 [AI_CONTEXT](project/AI_CONTEXT.md), 승인된 작업과 다음 순서는 [NEXT_WORK](project/NEXT_WORK.md), 변경·검증 이력은 [DEV_LOG](project/DEV_LOG.md)를 기준으로 확인합니다. 이 문서는 장기 작업·Git·검증 원칙을 관리합니다.

Python 3.12와 Docker Compose를 실행 기준으로 사용합니다. FastAPI·Pydantic v2·SQLAlchemy 2·Alembic·PostgreSQL·pytest를 사용하며 기능별 모듈형 모놀리스를 유지합니다. Google 인증은 구현됐고 다른 공급자와 WebSocket은 별도 승인 작업입니다.

기존 Firebase 사용자·데이터 이관이나 UID 연결을 전제로 하지 않고 신규 서버의 데이터를 별도로 관리합니다. 이는 기존 개발 DB를 초기화하거나 Firebase를 삭제하라는 지시가 아닙니다. 비로그인 앱 실행과 합의된 공개 조회를 허용하되 임시 UID·익명 회원·사용자별 데이터를 자동 생성하지 않는 방향으로 설계합니다. 사용자 식별이 필요한 기능의 인증·권한은 서버에서 검증합니다.

배포 예정 환경은 Lightsail Linux amd64, 운영 프록시 후보는 Caddy입니다. 초기에는 Cognito·Lambda·API Gateway·RDS·Redis·Kafka·Kubernetes·마이크로서비스를 전제로 추가하지 않습니다. S3·FCM 및 다른 인프라는 실제 요구가 생기면 검토합니다. 이 방향의 변경이 필요하면 이유와 영향을 제시하고 합의합니다.

## 작업과 Git

1. AGENTS → 협업 규칙 → NEXT_WORK → AI_CONTEXT → 관련 계약 순서로 확인한 뒤 요청 범위·완료 조건과 실제 Issue 본문·최신 댓글·Git·코드를 대조합니다. 인계할 때도 최신 댓글을 확인합니다. 불일치는 근거를 확인해 문서를 갱신합니다.
2. 브랜치명에는 이슈 번호를 붙이지 않고 큰 작업 범위를 사용합니다(예: `feat/account-management`, `feat/authentication`). 먼저 해당 범위의 진행 중인 브랜치를 확인하고 네이티브와의 관련 요청·답변·보완을 같은 브랜치에서 이어갑니다. 새 이슈나 댓글만으로 분기·전환하지 않습니다. 적합한 기존 브랜치가 없거나 별도 범위의 분리가 필요할 때 `feat/`, `fix/`, `refactor/`, `test/`, `docs/`, `chore/` 중 목적에 맞게 만듭니다. 관련 이슈 번호는 커밋·문서·댓글에 기록합니다.
3. 작은 변경은 짧은 설명으로 진행합니다. 인증·데이터 구조·공용 계약에 영향을 주면 필요한 수준의 설계와 검증 계획을 Issue나 PR에 남깁니다. 제품 결정이 부족하면 자료를 요청하되 독립적으로 가능한 조사는 계속합니다.
4. 작업 구간을 완료하면 필요한 검증과 문서 갱신 후 해당 구간을 작업 브랜치에 커밋합니다. 2026-10-21 사용자 상시 지시이며 커밋마다 재승인을 요청하지 않습니다. 작은 편집마다 커밋하는 뜻은 아닙니다. 네이티브에 구현 테스트·확인을 요청할 때는 검증된 해당 구간의 커밋들을 묶어 push하고 원격 확인을 마친 뒤 Issue로 인계합니다. 이 인계용 게시에는 기존 상시 승인을 적용하며 별도 PR·merge·배포 승인으로 확대하지 않습니다. 범위 안의 수정과 검증을 수행합니다. 오류는 재현·로그·직전 변경을 근거로 분석하고 같은 실패를 반복하면 접근을 재검토합니다.
5. 게시가 승인되면 최신 원격 main과 충돌 여부를 확인하고 PR로 통합합니다. 예상하지 못한 원격 변경은 임의로 덮어쓰지 않습니다. 운영 배포 버전은 향후 태그나 배포 기록으로 식별합니다.
6. 단계 종료 시 NEXT_WORK는 다음 실행 계획으로 갱신하고 상세 완료·결정·검증·장애는 DEV_LOG에 누적합니다. AI_CONTEXT는 핵심 상태·링크만 유지합니다. 완료 보고와 문서에서 브랜치·commit·push·PR·merge·배포와 남은 로컬 변경을 구분합니다.

### 브랜치 수명과 완료 후 정리

기본 보존 브랜치는 main과 dev입니다. 진행 중인 작업은 큰 범위별 작업 브랜치에서 수행하며, 보통 main·dev·현재 작업 브랜치 정도를 유지합니다. 하나의 작업 브랜치가 여러 이슈를 다룰 수 있습니다. 작업 브랜치를 하나로 제한하지 않지만 별도 범위의 병행 작업에 필요한 경우에만 추가합니다. 개별 이슈의 완료만으로 아직 관련 협업 작업이 진행 중인 범위 전체를 완료로 처리하거나 브랜치를 교체하지 않습니다.

작업이 완료되어 dev에 병합되고 원격 push까지 성공하면 해당 작업 브랜치를 로컬과 원격에서 삭제합니다. 사용자가 확정한 상시 규칙이므로 이 조건을 충족하는 정리는 별도 승인 요청 없이 수행합니다. 후속 작업은 최신 dev에서 새 브랜치를 만듭니다. Flutter의 후속 검증 대기만으로 이미 통합된 Backend 작업 브랜치를 계속 보관하지 않습니다.

삭제 전 실제 로컬·원격 ref와 dev 포함 여부, 미커밋·미통합 변경, 다른 worktree 또는 작업자의 사용 여부를 확인합니다. 삭제할 브랜치에서 벗어난 뒤 로컬은 `git branch -d`, 원격은 해당 브랜치만 지정해 삭제합니다. main/dev는 정리 대상으로 삼지 않습니다. squash 등으로 단순 포함 검사가 불가능하거나 원격에 예상하지 못한 변경이 있으면 이력·내용을 검토하고 불명확한 브랜치는 보존합니다. 강제 삭제나 공유 이력 재작성으로 우회하지 않습니다.

완료 보고와 DEV_LOG에 병합·push 결과 및 삭제한 브랜치를 남기고 NEXT_WORK·AI_CONTEXT의 현재 브랜치 상태를 갱신합니다. 브랜치 삭제는 통합된 커밋이나 기록을 삭제하는 작업이 아닙니다.

일반 구현 선택마다 추가 승인을 요구하지 않습니다. 별도 승인 대상은 데이터 파괴, 운영 변경, 외부 게시 등 실제 영향과 현재 사용자 요청 범위를 기준으로 판단합니다. 긴급 수정도 작업 브랜치와 필요한 검증을 유지합니다. 사용자 변경·로컬 자료를 덮어쓰거나 임의로 reset·브랜치 삭제하지 않습니다.

별도 공유 방식을 채택하기 전까지 heo0328/lostparty-backend의 GitHub Issues를 공식 협업 채널로 사용하며 [공통 협업 규칙](API_COLLABORATION.md#공통-협업-규칙)을 따릅니다. 받은 요청의 결과는 같은 Issue에 회신하고 SHA·브랜치·push 상태·계약 영향과 검증 범위를 필요한 만큼 인계합니다. 변화 없는 상태·독립 내부 작업에는 일괄 댓글이나 테스트 요청을 요구하지 않습니다. 후속 담당·작업·완료 조건·대기 사유와 Issue/댓글 링크는 NEXT_WORK에 연결하고 수행 이력은 DEV_LOG, 상태 지도는 AI_CONTEXT에 둡니다. 상세 실행 방법과 장기 계약은 기존 문서로 연결합니다. Flutter 저장소의 브랜치 규칙은 Backend에 자동 적용하지 않습니다.

## 검증과 데이터 보호

Docker Compose가 기본 실행 환경이며 WSL 시스템 Python을 변경하지 않습니다. 기능 변경에는 의미 있는 최소 검증을 적용합니다. pytest는 격리 PostgreSQL 테스트 환경에서 사용합니다. 인증·타인 자원 접근·권한 위조, 동시성·중복 요청·원자성·실패 시 rollback은 해당 기능을 구현할 때 검증합니다.

PostgreSQL 제약과 트랜잭션을 검증할 때는 개발·운영 DB와 분리된 PostgreSQL을 사용합니다. mock이나 다른 DB 결과만으로 PostgreSQL 동작을 검증했다고 보고하지 않습니다. DB 구조 변경은 Alembic migration과 적용·복구 계획을 함께 검토합니다.

`scripts/verify.py`는 DB 쓰기와 컨테이너 중지·재생성을 포함하므로 단순 상태 확인용으로 실행하지 않습니다. API 변경은 [계약 검증 절차](API_COLLABORATION.md)를 따르고 문서만 변경하면 내용·참조 경로·`git diff --check`를 확인하고 코드 테스트를 불필요하게 반복하지 않습니다. 실패·미실행·기존 실패를 구분합니다. OAuth 모의 검증과 실제 제공자·모바일 callback 검증도 구분해 인계합니다.

운영 배포는 별도 작업입니다. 대상과 승인 범위를 확인하고 개발·테스트·운영 자격 증명을 분리하며, 관련 테스트·계약·마이그레이션·백업·복구·롤백을 검토합니다. 백업 파일 존재와 복원 검증은 다릅니다. 운영 비밀정보 변경과 데이터 삭제는 별도 승인 대상입니다. 자동 배포·모니터링·백업은 현재 구현된 것으로 간주하지 않습니다.
