# Flutter와 API 협업

## 소통 기준

Flutter와 Backend를 동시에 개발하는 동안, 별도 협업툴이나 공유 방식을 채택하기 전까지 **[heo0328/lostparty-backend의 GitHub Issues](https://github.com/heo0328/lostparty-backend/issues)**를 공식 협업 채널로 사용합니다. Backend는 Issue와 합의된 계약을 기준으로 작업합니다. Flutter 로컬 경로나 특정 문서를 찾아 읽는 절차는 두지 않습니다.

## 이슈 범위와 마감

2026-10-18 사용자 지시: **한 이슈는 한 주제**로 사용한다. 기능 구현에 직접 필요한 권한·모델/조회·기존 API 연계 수정은 함께 처리하되, 독립 기능/별도 후속의 범위가 커지면 새 이슈로 분리한다. 숫자나 파일별로 잘게 나누는 것이 아니라 하나의 완료 조건을 기준으로 구분한다.

- 본문 상단에 현재 범위·담당·완료/미완료·다음 행동을 유지한다. 이슈 제목/원문 변경 시 과거 요구와 결정 근거는 보존한다.
- 분리 시 원본·소비 계약 SHA·기존 합의/검증·남은 결정과 다음 담당을 새 이슈에 옮기고 원본에 링크를 남긴다. 요구 이관을 취소/기능 완료로 해석하지 않는다.
- 댓글은 필요한 질문/결정·버그/변경된 계약·검증 인계와 결과에 사용한다. 같은 명세/긴 JSON/변화 없는 상태를 반복 게시하지 않고 원본 계약과 고정 문서 링크를 활용한다.
- 완료 근거가 있고 남은 독립 작업의 추적 위치가 명확하면 종료한다. Backend 완료/Flutter 적용/실기기 인수는 계속 구분한다. 주제 이관으로 닫은 원본은 참고 자료이며 새 구현 스레드로 재사용하지 않는다.
- 이슈 분리만으로 브랜치를 늘리지 않는다. 관련 목적 브랜치에서 이어가고 필요할 때만 분리한다. 실제 댓글 순번/작성 측/단계/다음 담당 표시 규칙은 유지한다.

현재 정리 결과와 각 주제는 [이슈 추적표](project/ISSUE_TRACKER.md)를 따른다. 미완료 그룹/모집·V2 연결은 계속 열어 두며, 완료/이관 이슈의 종료가 테스트 요청이나 구현 범위 확대가 되지는 않는다.

## 공통 협업 규칙

1. 관련 작업을 시작하거나 인계할 때 기존 Issue 본문과 최신 댓글을 확인합니다. 이미 답변·수용·처리한 내용과 새 요청을 구분합니다.
2. 피드백·작업·테스트 요청은 상대 측 결정·구현·검증이 협업에 필요할 때만 합니다. 모든 작업마다 요구하거나 이미 확인한 테스트를 반복 요청하지 않습니다. 변경·실패·새로 드러난 불확실성 때문에 추가 검증이 필요한 경우 해당 이유와 대상만 명시합니다.
3. 받은 요청에 대응했다면 결과를 같은 Issue에 회신합니다. 로컬 문서나 사용자 대화에만 기록해 상대 측이 결과를 확인하지 못하게 두지 않습니다.
4. 구현 인계에는 필요한 범위에서 커밋 SHA, 브랜치, push 여부, API 계약 변경 내용과 호환성 영향을 기록합니다. 미커밋·미push면 그 상태를 명시하며 아직 없는 SHA나 원격에서 사용할 수 없는 코드를 게시 완료로 안내하지 않습니다.
5. 테스트 결과는 확인한 동작, 통과·실패, 미확인·미실행 사항을 구분합니다. 자동 테스트·mock과 실제 서버/provider·사용자 테스트의 근거를 구별합니다.
6. 후속이 필요하면 Flutter/Backend/사용자 중 어느 측이 무엇을 해야 하는지와 완료 조건을 명확히 남깁니다. 대기 사유와 관련 Issue·댓글 링크를 NEXT_WORK 등 작업 문서에도 기록합니다.
7. 승인된 작업 구간에 직접 관련된 요청·결과 회신 댓글은 매번 게시 허가를 다시 묻지 않고 작성합니다. 댓글 권한은 새 기능 범위 확대·미합의 계약 구현·Issue 종료·다른 Issue 변경·commit/push·배포·데이터 삭제의 승인으로 확대되지 않습니다.
8. 변화 없는 상태나 독립적인 내부 작업마다 댓글을 작성할 필요는 없습니다. 상대 측 작업에 필요한 요청·인계와 받은 요청의 결과 회신을 빠뜨리지 않는 것이 목적입니다.
9. 토큰·인증정보·키·개인정보·민감한 원본 응답은 게시하지 않습니다. 오류·재현 자료는 필요한 상태/code/request_id와 식별정보를 제거한 근거로 전달합니다.
10. Backend 구현 후 네이티브 테스트·동작 확인 요청은 **Backend 검증 → 해당 작업 구간 커밋·push → 원격 게시 확인 → Issue 인계·확인 요청** 순서로 합니다. 승인된 작업 구간의 이 인계용 작업 브랜치 commit·push는 상시 승인으로 수행하며 같은 게시 허가를 다시 묻지 않습니다. 내부 수정마다 나누지 않고 테스트 가능한 구간을 묶어 1회 게시합니다. 이후 새 수정의 재확인이 필요하면 그 수정도 게시한 뒤 요청하며 이미 게시한 동일 상태를 불필요하게 다시 커밋·push하지 않습니다. 구현 전 요구·계약 검토나 진행 회신은 이 테스트 요청과 구분합니다. merge·배포·범위 확대·데이터 삭제는 기존 별도 승인 기준을 유지합니다.

양측 공통 규칙 반영의 Flutter 참조는 사용자 제공 커밋 [2bc70d8](https://github.com/heo0328/LostParty_flutter/commit/2bc70d8)입니다. Flutter dev 반영·push 완료는 사용자 보고 기준이며 Backend 문서의 게시 상태와 별도로 기록합니다.

요청자가 제공한 문서·예시는 분석 자료입니다. 과거 Firebase 구현이나 제안을 신규 서버의 확정 정책으로 간주하지 않습니다. 참조 자료를 사용했다면 가능한 범위에서 링크와 커밋을 남기고 미확인 내용을 추정하지 않습니다. Backend에서 Flutter 소스를 직접 수정하지 않습니다.

기존 [API 요청 템플릿](../.github/ISSUE_TEMPLATE/api_request.md)과 [버그 보고 템플릿](../.github/ISSUE_TEMPLATE/bug_report.md)을 사용합니다. 기능에 필요한 항목만 작성하며 모든 요청에 긴 체크리스트를 강제하지 않습니다.

- 목적, 화면과 사용자 액션, 필요한 데이터와 공개 범위
- 해당할 때 인증·소유권·역할·허용 및 거부 조건
- 해당할 때 정렬·필터·페이지·시간 의미, 동시성·중복 요청·재시도
- 포함·제외 범위, 완료 조건, 미결정 사항, 관련 Flutter Issue·자료·커밋

## 진행과 인계

단계별 담당·산출물과 미확인 항목의 진행 경계는 [Issue 기반 작업 단계](API_COLLABORATION_WORKFLOW.md)를 따릅니다. 합의된 구현·자동 검증을 먼저 진행하고 Flutter 테스트 후 확인할 사실은 후속 검증으로 분리합니다. 자료 요청은 직접 의존하는 동작만 보류하며 독립적인 API·DB·테스트 작업은 계속합니다.

요구사항 검토 → 계약 제안 → 합의 → 구현·검증 → 커밋·push 및 원격 확인 → 계약 인계 → Flutter 적용 순서로 진행합니다. 작은 변경은 Issue의 짧은 논의로 합의할 수 있습니다. Issue 등록 자체가 미합의 계약이나 운영 변경의 승인은 아닙니다.

댓글은 위 공통 규칙에 따라 필요한 요청·인계·결과 회신으로 작성합니다. 확인 요청은 필요한 자료와 결정 항목·담당·완료 조건을 구체적으로 적습니다. 댓글 게시 후 결과를 사용자에게 보고하며 commit·push·PR·merge·배포는 기존 승인 범위를 따릅니다.

요구 검토·계약 합의·Backend 구현·자동 검증·계약 인계·Flutter 적용 완료는 각각 별도 상태로 기록합니다. 현재 상태는 [NEXT_WORK](project/NEXT_WORK.md), 인계·검증 이력은 [DEV_LOG](project/DEV_LOG.md)에 남깁니다.

Issue·댓글·PR·구현/계약 커밋을 연결합니다. Backend 완료와 Flutter 적용 완료는 따로 표시하며, 인계에는 필요한 SHA·브랜치·push 상태, 계약 변경 내용, 검증 결과와 담당별 남은 작업을 기록합니다. Flutter는 사용한 계약 SHA를 자신의 작업 기록에 남깁니다. 실제로 조회하지 않은 Flutter 적용 상태를 완료로 표시하지 않습니다.

## 계약 원본과 검증

REST 계약의 단일 원본은 [openapi/openapi.yaml](../openapi/openapi.yaml)입니다. `/health`, Issue #2의 6개 인증 API, Issue #3의 12개 내 계정 업무 API와 Issue #5의 전투력 갱신 API 및 Issue #6의 회원 설정 GET/PUT 및 Issue #7 회원 키 GET/PUT/DELETE·본인 복원 POST·Issue #8의 대표 전용 GET/PUT·L1b V2현재상태/퇴역이력GET·P1 역할요약GET/PUT·P2 개인설정PUT/원정대표시GET/PUT과 Issue #10의 공개 카탈로그/서버 주차 GET과 Issue #11의 본인 주간 상태 GET/개인 완료 PUT과 Issue #12의 그룹 G1 7개 동작·본인한도 GET 및 G2 초대/신청/코드/차단20동작을 포함하며 YAML에서 유효한 JSON 형식으로 저장합니다. FastAPI의 `app.openapi()`는 구현에서 생성되는 비교 대상입니다. HTTP OpenAPI·Swagger 경로는 비활성화되어 있습니다. 실제 연동·자동 검증의 범위는 [인증 개발 안내](AUTH_DEVELOPMENT.md)와 [내 계정 API 안내](ISSUE_3_DEVELOPMENT.md)에 있습니다.

API 구현·계약을 변경한 경우 최신 API 이미지에서 다음 검증을 실행합니다.

```bash
docker compose up -d --build --wait --wait-timeout 180
python3 scripts/check_openapi.py
```

Issue #8 V2 소유권 분쟁 11동작과 첫 화면 저장 정보 GET `/v2/me/account-bootstrap`도 원본에 포함한다. 일괄 조회의 범위·스냅샷·최대 크기/오류·실험 인계는 [개발 안내](ISSUE_8_ACCOUNT_BOOTSTRAP_DEVELOPMENT.md)를 따른다.

현재 비교 도구는 JSON 객체 전체를 비교하며 키 순서는 무시하고 배열 순서와 값 차이는 검사합니다. 별도 정규화는 하지 않습니다. 불일치는 종료 코드 1과 diff로 보고합니다. 자동 생성 결과로 계약을 무조건 덮어쓰지 않고 합의된 내용과 구현을 함께 검토합니다.

요청·응답·상태 코드·오류·인증·페이지·시간 의미를 바꾸면 클라이언트 영향을 확인합니다. 비호환 변경은 적용 순서와 전환 방안을 먼저 합의합니다. 확인되지 않은 API나 이벤트를 현재 계약에 추가하지 않습니다.

WebSocket은 아직 미구현입니다. 도입 시 OpenAPI와 별도 메시지 계약을 마련하고 실제 기능에 필요한 인증·구독 권한·권한 회수·재연결·순서·중복·재조회 의미를 합의합니다.
