보존된 초기 설계 검토다. 현재 제품/계약·구현·dev 반영·게시 기준은 [최신 계약](refresh-candidate-contract.md), 구현 `8f29271d610aad83021ec3a00e5879f2adda76d5`를 따른다. 아래 미결정/미구현은 당시 기록이며 Issue58 확정으로 해소된 항목을 다시 질문하지 않는다.

2026-11-17 / Issue18 전체4 Native 설계 검토 요청에 대한 Backend 검토. 목적 브랜치 `feat/roster-refresh-policy`. 구현/DDL/OpenAPI 확정·서버 적용·provider 호출 요청이 아니다. 기존 미커밋 Issue57 완료 정정은 보존한다.

## 최신 제품 확정 — Native 전체5 반영

회신 직전 [전체5 Native 사용자 확정](https://github.com/heo0328/lostparty-backend/issues/18#issuecomment-6942423798)을 추가 확인했다. 다음 항목은 이제 제품 미결정이 아니다: 신규도1700 이상/선택저레벨 유지/null 임의해석 금지, 최초 등록·인증1700 최초1회, 실패 신규후보는 조회 가능한 결과 카드의 명시 재시도만/결과불명 원ID·본문 복구/saved 경고 성공 소모, 신규후보도 나이스단OFF 적용·실패집계 제외/개별manual 허용/수동전체는 기존선택만. 아래 전체4 검토의 해당 질문은 이 확정으로 해소한다.

실패는 blocked 상태로 보존하고 목록 재조회/앱 재실행만으로 재시도 권한을 재발급하지 않는다. 명시 재시도는 terminal 실패 확인 후 새 command_id로, 후보 generation/CAS와 원자적으로 연결한다. 새ID만 보내 실패후보를 automatic으로 재실행하는 우회는 거절하는 서버 권한 계약이 필요하다. 최소안은 기존 manual 개별명령을 결과 카드의 명시 행동으로 사용하고 성공 시 동일 후보를 완료하는 방식이다. 서버가 ‘실패후보 재시도’라는 의미/시도 이력을 식별해야 하면 candidate_id/generation과 명시 목적을 함께 전달하는 필드가 필요하며 DTO는 미확정이다.

나이스단OFF 보류는 실패/완료가 아니며 현재 자동적격 상태로 투영한다. 설정 변경으로 적격이 되면 미완료 후보를 재평가할 수 있으나 terminal 실패의 명시 재시도 제한을 초기화하지 않는다. 사용선택과 후보의 합집합 중복은1건으로 처리하고, 기존 사용선택의 앱 실행1회 정책은 보존한다.

인증 관찰은 현재 서버가 정상 파싱·proof/대상/credential·소유 scope를 검사한 roster 관찰만 같은 인증 성공 트랜잭션의 기준선/후보 생성에 재사용할 수 있다는 제안이다. 인증 장비 관찰을 상세 분석 saved로 간주하거나 재사용하지 않는다. 프로필/분석에 필요한 armory는 별도 검증된 수집이 필요하다.

## 목적과 현재 근거

사용 선택 ∪ 신규 발견/첫1700 도달의 상세 분석 후보를 서버가 결정하되 Activity·대표·참가 자격을 바꾸지 않는다. 원정대 수동 전체는 선택 집합, 자동/인증 후1회는 합집합이라는 Native 제안과 세부 제품 미확정을 구분한다. 전투 레벨을 새 필터로 도입하지 않는다.

현재 `analysis/service.eligible`은 automatic에 Activity를 요구하고 나이스단 설정이 OFF면 현재 소유·활성 원정대의 같은 직업1700 이상 수가2 이상일 때 제외한다. manual은 이 필터를 우회하지만 owned_character와 revision 검증은 유지한다. 미선택 신규후보에 manual을 쓰거나 먼저 활동등록하는 우회는 허용하지 않는 방향이다.

`owned_refresh.validate → reconcile`은 정상 소유 목록을 트랜잭션으로 반영한다. `Character.summary`의 현재 item_level에는 최초 관찰/첫 도달 이력이 없고, RosterTransition은 누락/재등장 증거로서 매번의 레벨 관찰 원장이 아니다. AnalysisFetch는 짧은 동시 관찰 공유이고 명령 원장은 완료24시간 이후 원ACK 보장을 종료하며 정리된다. 어느 것도 장기 후보 완료/명시 제외 저장소를 대신하지 못한다.

옛 설계5fff83b는 현재 로컬 Git 객체에 없어 원문 검증하지 못했다. Issue18 전체2 Backend 초안·현재 proposals와 코드를 기준으로 검토했다. 당시 경로·브랜치/DB0016 안내를 현 상태로 재사용하지 않는다.

## 최소 영속안 — 제안

기존 #18의 기준선+캐릭터 정책 구조를 공통 관찰 사실 저장소로 구체화하고, 자동 활동 추가와 상세 분석의 처리 상태를 분리한다. 새 관찰 원장을 목적별로 중복 생성하지 않는다. 두 논리 구조 후보이며 확정 DDL/표 수 약속은 아니다.

- 회원·canonical account·ownership_revision별 정책 기준선: 도입 정책 버전/설정 시점, 기존/신규 소유 연결 구분. 첫 설정/재등록 처리는 제품 결정과 결합한다.
- 같은 범위+canonical character UUID별 정책 상태: 최초 정상 관찰·최초 유효1700 도달(관찰 식별/시각·레벨 근거), legacy_unknown, 명시 제외 의도/버전. 상세 후보에는 안정적인 candidate_id·generation·reason, pending/running/succeeded/blocked, 처리 명령 참조·임대 만료·시도 횟수/다음 가능 시각·마지막 오류/완료 근거를 둔다. 미래 활동 자동추가의 applied 상태와 공유하지 않는다.

기존 선택/summary만 보고 opt-out/과거 첫도달을 소급 생성하지 않는다. 도입 전 캐릭터는 보수적 기준선으로 유지하고, 도입 뒤 정상 관찰에서 확인된 미도달→1700 도달만 첫 문턱 사건으로 취급하는 안이다. 레벨null은0으로 해석하거나 기존 알려진 도달 사실을 취소하지 않는다. 첫 도입 시 이미1700인 과거 미선택과 도입 후 새 인증의1700 첫후보는 구분한다. 최초 관찰 시 null이었다가1700 확인된 경우 후보 인정 여부도 제품 결정이 필요하다.

한 후보가 신규발견+첫1700을 함께 만족해도1개다. 성공 후 반복 목록 관찰/자동 실행/역할 전환/이름 변경만으로 재발급하지 않는다. 누락/재등장만으로도 새 후보를 만들지 않는다. 다른 소유자/소유세대에는 선택·제외·성공을 승계하지 않는다. 같은 소유세대의 동일 회원 재등록은 후보 완료를 유지해 반복 지급을 막는 안을 권장하나 제외 복원·삭제 후 자료 수명은 기존 #18 미결정으로 남긴다.

## 트랜잭션과 중복

1. provider I/O는 기존대로 DB mutation lock 밖에서 수행한다. 최신 소유/등록/claim·usable·관찰 범위/세대를 검사한 정상 목록 반영 트랜잭션에서 기준선/후보를 upsert한다. 캐시·stored summary·HTTP200만으로 사건을 만들지 않으며 기존 observation 범위를 소멸/이전의 완전성 증거로 확대하지 않는다.
2. 미선택 후보는 automatic 권한의 별도 근거로 서버가 검사한다. 현재 소유·usable·명시 제외·설정/정책 버전·나이스단 제품 규칙을 시작과 저장 때 검사한다. 동시 선택 변경은 CAS 충돌/후보 취소로 처리해 최신 의도를 보존한다. 대표·Activity·configured 상태는 변경하지 않는다.
3. 같은 후보는 DB 유일키와 행 잠금/조건부 임대 획득으로 두 기기에서1개 명령만 실행한다. 후보 임대와 기존 명령30초 임대/실행세대를 연결한다. 임대 만료만으로 기존 running 명령을 무시한 새 호출을 시작하지 않는다. 소유/세대 상실·취소된 실행은 저장 못하도록 fencing한다. 현재 AnalysisFetch의 순간 공유만으로 중복 완료를 해결하지 않는다.
4. 저장 시 최신 권한·설정·candidate generation·summary CAS를 재검사하고 CharacterRoleSummary 저장+후보 succeeded+원ACK를 같은 트랜잭션에서 commit한다. 실패/rollback이면 후보도 완료되지 않는다. 후보를 실행 시작/관찰 성공/화면 표시만으로 소모하지 않는다.
5. 사용 선택 경로와 후보 경로가 겹치면1개 분석 명령으로 처리한다. 동일 canonical/소유세대/유효 후보를 대상으로 시작한 manual/선택 경로의 saved도 후보를 완료하는 안을 권장한다. 다른 기기의 CAS 패자는 최신 후보 상태를 조회해 불필요한 재분석을 피한다. ACK 복구는 최신 권한/후보 검사보다 먼저 적용해 원래 결과를 보존하되 회원·소유 접근 검증은 유지한다.

명시 제외를 최신 transaction에서 우선하려면 최초 start snapshot과 저장 CAS에 설정/제외 정책 버전을 포함해야 한다. 이는 현재 automatic 권한과 경합 응답의 계약 변경이므로 현재 service 코드가 이미 지원한다고 안내하지 않는다.

## 최소 소비 계약 후보 — 미확정

현재 분석 POST의 items 최대50·예산20초·동시2·item command_id/trigger·summary ownership/lifecycle CAS를 재사용한다. 후보 경로의 automatic에만 candidate_id/generation·expected_policy_version 같은 추가 근거를 제안하며 서버는 해당 입력의 권한을 검증한다. 필드를 추가하면 같은 command_id의 body digest도 달라지므로 기존 pending 본문을 바꿔 보내지 않는다. 기존 pending은 종전 본문/계약으로 복구하고 신규 후보는 새 명령으로 시작하는 전환이 필요하다.

응답 후보는 현재 bootstrap의 원정대 항목 또는 범위가 정해진 profile에 opt-in projection으로 policy_version·baseline 상태와 후보별 character_id/candidate_id/generation/reason/state/next_attempt_at/미해결 command_id를 추가하는 안이다. 최대20원정대/각200캐릭터의 기존 상한과 body 크기를 구현 전 검토한다. GET은 읽기 전용/no-store이며 관찰/후보 생성·자동 활동저장을 하지 않는다. refresh 후 이 투영을 무효화/재조회하고, saved 원ACK와 현재 후보 state를 분리한다. 새 전용 GET 필요 여부/기존 profile 선택자는 Native 호출 흐름을 대조해 확정한다. Activity selection DTO를 상세후보 권한으로 전용하지 않는다.

## 실패/결과불명과 제품 질문

기존 pending/in_progress/unknown은 같은ID·같은본문 복구를 유지한다. 완료 ACK24시간과 미완료 최대48시간 경계는 후보의 영속 수명/성공 근거와 다르다. 원장 정리 후 원명령 ACK 복원을 약속하지 않는다. 조회된 후보 succeeded면 자동 신규명령을 생성하지 않고 저장정보를 읽는다. 후보에 미해결 상태가 남으면 원장의 복구 가능 여부를 서버가 대조하고 임대/fence를 정리한 뒤에만 재시도를 허용한다.

terminal failed는 완료 후보가 아니다. 그렇다고 다음 앱 실행마다 새ID를 만드는 것도 금지하는 안이다. 기존 retry none/new_command·rate-limit retry_at은 최소 제한이며 후보 자동 재시도 횟수/간격·재개 조건은 별도 정책이다. 초기안은 실패를 blocked로 보존해 무한 자동 반복을 막고 사용자 명시 재시도나 합의된 횟수/백오프에서만 해제하는 것이다. skipped와 나이스단OFF는 성공으로 소모하지 않는다.

제품/Native 결정 요청:
- 신규도1700 이상, 선택된 저레벨 유지, null 보류·첫등록1700 최초1회·과거 미선택 유지의 확정 여부와 null→유효1700 처리.
- 미선택 후보를 나이스단OFF 예외로1회 허용할지, 기존처럼 보류할지. 명시 사용제외가 활동 자동추가만 금지하는지 자동 상세 분석도 금지하는지. 보수적 권장은 의도적으로 제외된 캐릭터의 자동 상세 분석도 보류하는 것이다.
- unconfigured/needs_reconfiguration에서도 분석만 허용할지. 선택/대표를 자동 수정하지 않는 점은 유지한다.
- terminal 실패의 자동 재시도 횟수/간격·수동 재시도 UX, 같은회원 재등록의 제외 복원/기준선 수명.
