# 소유권 분쟁 최종이전의 그룹·레이드 영향 검토

2026-10-31 / feat/ownership-dispute-policy / 사용자 검토·Flutter 협의용. 기존 [소유권 계약](README.md)·[Issue15](https://github.com/heo0328/lostparty-backend/issues/15)의 PARTY_IMPACT_REVIEW_REQUIRED 후속을 사용자가 우선 정리하도록 요청했다. 아래 제안은 미합의·미구현이며 기존 API/DB/실행서버를 변경하지 않는다.

## 먼저 구분할 사건

V2 장비인증 성공으로 타인 소유 원정대에 도전하면24시간 분쟁이 시작된다. 이 시점은 최종소유이전이 아니다. 현 소유자의 방어성공·도전자취소·무효화에는 소유이전 후처리를 적용하지 않는다. 24시간 이후 worker가 실제 final transfer를 확정할 때의 영향을 논의한다. settle200은 예약ACK이며 이전완료 증거가 아니다.

## 확인한 현재 구현

| 원본·연결 | 현재 의미·할 수 있는 식별 |
|---|---|
| Account.owner_id / ownership_revision | 특정 원정대의 현재 소유자/소유세대. 사용자 계정 전체의 정지/불량 상태와 다르다. |
| Character.account_id | 캐릭터에서 원정대로 FK 연결. 이름/표시문구로 추정하지 않는다. |
| Registration.user_id / account_id | 사용자의 등록항목과 원정대 연결. 이전 사용자의 등록은 삭제 대신 ownership_lost로 조회된다. |
| Configuration(user_id,account_id), Activity(settings_id,character_id) | 사용자·원정대별 설정/활동. 이전 원정대의 기존설정만 종료하고 새 소유자 설정은 unconfigured로 시작한다. |
| GroupMembership(group_id,user_id,character_id) | 그룹 가입은 사용자 단위이며 캐릭터는 표시/자격참조다. 원정대별 가입 여러 행이 아니다. |
| Group.representative_character_id / representative_user_id | 그룹 공통대표 참조. 현재 소유를 잃으면 needs_update로 읽으며 사용자그룹장 관계와 구분한다. |
| SubjectCharacterReference(character_id,ownership_revision) | 신규 그룹가입/초대/차단 근거의 캐릭터·소유세대. 과거 참조없는 자료를 이름으로 자동연결하지 않는다. |
| RecruitmentAssignment(user_id,character_id,ownership_revision,room/item/round/membership IDs) | 사용자의 어떤 캐릭터가 어떤 모집/raid에 참가했는지와 당시 소유세대. Character→Account로 영향원정대를 찾는다. |
| CycleAssignment / CycleMember / RoomCycle / CycleGeneration | 참가를 실제 주차·세대·공대장과 연결. 같은사용자의 반대T 또는 다른원정대 참가를 독립 식별한다. |
| WeeklyState / WeeklyOccupancy / TimeReservation | 주간점유·정확한 참가 assignment와 시간예약의 연결. 개인완료/역사snapshot과 현 예약을 구분한다. |
| CycleApplication.selection / ContinuationChoice | pending신청은 저장선택, 계속참가는 character_id/ownership_revision로 영향대상을 확인한다. 모든 참조가 FK 한 줄로만 이어지는 구조는 아니다. |

연결은 하나의 선형목록이 아니라 사용자·원정대·캐릭터·참가의 관계형 구조다. 명시적 현재 자료는 원정대 단위로 역조회해 영향계획을 만들 수 있다. legacy_unknown·참조부족/불일치는 확인불가로 남기고0건으로 가정해 강제정리하지 않는다.

현재 worker.apply_transfer는 그 원정대 캐릭터의 WeeklyState.active_party_id가 있으면 소유이전 전에 review_required/PARTY_IMPACT_REVIEW_REQUIRED로 보류한다. 자동탈퇴·자동승계·예약해제나 이전 후 참가교체 대기를 만드는 adapter는 없다. 기존 membership-actions는 사용자/실제T 명령이므로 원정대소유이전에서 leave_all을 그대로 호출하면 다른원정대/다른T·pending까지 정리할 수 있다. 전용 영향계획과 동일트랜잭션 처리설계가 필요하다.

## 사용자 예시의 현재 가능 여부

A사용자가 R/R1/R2 원정대를 가지고 있고 R이 B로 최종이전되는 경우:

- **그룹:** A의 그룹가입은 유지한다(현 동작). 그룹 활동목록은 현재소유·설정/활동을 읽으므로 R 캐릭터는 제외되고 R1/R2는 유지된다. 가입표시 캐릭터가 R이면 character_spec unavailable, 그룹대표가 R이면 needs_update가 될 수 있다. 가입표시/그룹대표를 R1로 자동교체하는 동작은 없다. B는 R을 얻어도 A의 그룹가입/그룹장/개인설정을 승계하지 않는다.
- **레이드:** R 캐릭터 assignment에서 실제T·세대/공대장·예약을 찾을 수 있다. R1/R2 참가와 과거완료를 보존한 정리/교체 설계는 가능하지만 현재 자동처리는 없다. 활성참가가 있으면 이전 자체가 보류된다. 따라서 ‘이전만 먼저 하고 현 참가를 나중에 정리’는 현 보류조건을 바꾸는 기능개발이다.
- **새 소유자 B:** 원정대의 canonical 캐릭터 ID는 유지하지만 A의 참가좌석/공대장/그룹/개인완료/분석을 승계하지 않는다. 새소유권을 얻었다는 이유만으로 A의 참가를 B참가로 바꾸지 않는다.

## 협의 제안 — 원정대/관계별 복구 필요, 사용자 전체 경고는 피한다

사용자가 제시한 두 방안은 모두 기술적으로 설계할 수 있지만 아직 정책확정이 아니다.

| 선택지 | 장점 | 결정해야 할 비용·경계 |
|---|---|---|
| 최종이전과 영향참가 자동정리 | 잃은캐릭터의 유효참가/예약을 남기지 않음 | 공대장승계/외부승계 일반전환/후임부재, 여러T/그룹/pending·예약·완료보존을 같은원자계획으로 정의해야 함 |
| 최종이전과 영향대상 복구필요 전환 | 기존사용자가 R1/R2 캐릭터로 참가를 교체하거나 관계정리할 기회 | 임시자리/예약의 보존기간·가입/일정/공대장권한 제한, 복구기한/기한후처리·조회공개를 정해야 함 |

검토 방향은 원정대별 기존 ownership_lost를 원본으로 삼고 영향받은 참가/표시참조에만 복구상태를 부여하는 것이다. user.status에 ‘문제사용자’를 넣어 R1/R2·다른그룹/레이드까지 제한하지 않는다. 다른참가자에게는 필요 범위의 ‘참가 캐릭터 인증 확인/교체 필요’를 안내하며, 분쟁당사자 신상·도전자·장비증거·진행경위는 공개하지 않는다. 상태값/문구/공개대상/DTO는 모두 소비검토 전 미확정이다.

내계정 갱신은 현재 서버소유/설정을 다시 읽는 진입점이다. 캐시/갱신성공만으로 상실한 소유권을 복원하거나 옛참가를 재활성화하지 않는다. R1/R2의 유효캐릭터를 명시선택하고 최신소유/레벨/역할/구성/주간점유/그룹·CAS/확인토큰으로 실제참가변경을 검증해야 한다. 교체 허용은 기존 character-change 입구가 검토상태에서 동작하는지까지 설계해야 하며 자동재참가·새소유자상속은 하지 않는다.

## Flutter와 먼저 정할 항목

1. 분쟁 시작은 기존소유권 유지, 최종이전 때만 영향처리한다는 사건 경계와 방어성공/취소의 무변경 처리.
2. 그룹은 사용자가입 유지·상실원정대 활동 제외를 기본검토로 하되 가입표시/그룹대표와 그룹장 역할의 교체 UX, 남은 유효원정대0개일 때 정책.
3. 레이드의 자동정리와 복구필요 전환 중 기본정책, 복구선택/탈퇴 주체·기한/만료, 예약·정원/공대장 권한을 어떻게 유지/해제할지.
4. 공대장 상실 시 기존 실제T 승계규칙을 적용할지, 언제 적용할지. 그룹소속과 참가/기록을 B로 넘기지 않고 R1/R2·반대T·완료/원origin을 보존할지.
5. 내계정/그룹멤버/모집상세에서 표시할 사실·공개대상과 쓰기후 재조회/late응답/소유세대 경계. 현재 UI에 필요한 영향을 먼저 확인한 뒤 정확한 계약·DB/명령 설계.

## 이번 확인과 미실행

기존 분쟁/그룹 기능4개 선택시험은 격리 PostgreSQL에서4PASS(12.13초, c3a0ef528b04)다. 실제worker의 이전·멱등/개인자료·그룹가입 비상속/활성참가이전보류와 소유상실의 그룹표시를 확인했다.

신규 tests/test_ownership_dispute_impact.py는0034/0035에서 원정대3개 중1개 소유상실 결과를 합성주입해 그룹활동6→4/기존사용자가입유지/상실ownership_lost·나머지2개owned와 설정버전보존을2PASS(11.63초, af9d6bd30019)로 확인했다. 이는 실제24시간 분쟁전체·레이드자동정리·복구명령 구현검증이 아니다. 실제소유이전은 기존선택시험의 별도근거다.

기존 Starlette/AnyIO 경고1/실행, 임시DB/네트워크 정리 성공. 실행별 선택을 전체프로젝트회귀로 표시하지 않는다. 제품코드·API/OpenAPI·DB스키마·실행서버/실회원·기기·자료정리/초기화·AWS/merge·Issue종료는 변경/실행하지 않았다. 정책합의 후 영향계획/상태/권한·원자성/경합·ACK/이력·역할별회복을 설계하고 별도구현/격리검증/실제반영을 구분한다.
