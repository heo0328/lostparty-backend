# Backend 개발 품질·데이터 책임·UX 판단 기준

[공식 협업 Issue21](https://github.com/heo0328/lostparty-backend/issues/21)의 요청에 따라 [공통 원문 — Flutter62240fe 고정본](https://github.com/heo0328/LostParty_flutter/blob/62240fe25711d26c478c295590c80114ebf69a6a/docs/architecture/DEVELOPMENT_QUALITY_AND_UX_STANDARD.md)을 Backend의 기존 작업 흐름에 맞춰 적용한다. AGENTS·개발/협업 규칙을 보완하며 별도 승인 절차나 일괄 리팩토링 지시를 추가하지 않는다.

Issue21은 사용자와 네이티브가 협의한 기준을 전달하는 용도로 종료한다. 전달 내용은 이 문서와 AGENTS·개발/협업 규칙에 보존하며 별도 회신·재수용/반복 검증 대기는 없다. 이후 승인된 작업에 이 기준을 적용한다.

## 사용자 경험과 구조 선택

사용자가 기능의 목적·대상 캐릭터/방/실제 주차·현재 상태를 이해하고 원하는 일을 쉽게 예측하며 수행하는 경험을 우선한다. 권한·보안·정합성은 이를 지탱하는 필수 조건이다. 서버 내부 편의를 위해 추가 화면·입력·반복 요청·장문 설명을 요구하지 않는다. 승인된 UX에 영향이 있으면 대안과 영향을 먼저 협의한다.

승인된 기능 작업에서 해결할 사용자 문제와 보존할 흐름, 데이터/정책·트랜잭션 책임, 기존 방식 유지/변경 이유와 영향받는 호출자, 필요한 검증을 작업 규모에 맞게 설명한다. 작은 수정은 관련 근거를 붙인 몇 문장이면 충분하다. 매 함수/작업마다 별도 설계서·Repository 계층을 만들지 않는다.

라우터는 입력/인증 경계와 HTTP 계약을 연결하고, 업무 서비스/명령은 현재 권한·CAS·정책/효과를 판단하며, 명령 실행 경계는 트랜잭션·원자성·원응답 저장과 최종 경계를 소유한다. 실제 기존 구조를 먼저 읽고 이 책임이 어디에 있는지 확인한다. 패턴 이름·코드/파일/API 수나 압축된 표현을 품질 지표로 삼지 않고 업무 규칙의 이해·수정·추적 가능성을 평가한다.

## 목적별 API와 데이터 갱신

독립된 목적·권한·수명의 API와 전체/부분 조회는 필요에 따라 유지한다. endpoint마다 권한·업무 정책·멱등/원자성 규칙을 복제하지 않고 적절한 공통 함수를 재사용한다. 합치기·분할·캐시 신설을 사전 결론으로 두지 않는다.

계약 변경/인계에는 해당하는 범위에서 다음을 명시한다.

- 기준 원본과 회원/환경·character/room/실제T 식별자 및 revision·스냅샷 시점/신선도
- 전체/부분 조회의 관계와 쓰기 후 바뀌는 자원, 갱신/무효화/재조회할 범위
- 저장/명령 성공과 후속 조회 실패, 진행중·중복·결과불명·확정거절의 구분
- 원명령 ACK 복구와 현재 상태 조회의 구분, 회원/권한/주차 전환·지연응답에 필요한 근거

모든 인계에 같은 긴 표를 붙이지 않는다. 소비자가 기존 자료·진행요청을 재사용할 수 있는지 검토하되 서버 명령의 최신 권한/CAS/정원·충돌 검증을 앱 캐시로 대신하지 않는다. 민감·일회성 권한 응답의 no-store를 효율을 이유로 완화하지 않는다. 화면/카드마다 새 API를 만드는 것을 기본 해법으로 삼지 않는다.

## 작업 수명·검증·측정

서버가 소유한 세션·DB 연결·외부 HTTP·백그라운드 작업의 종료/타임아웃·취소/캐시 상한을 변경 영향에 맞춰 확인한다. 네이티브 화면 작업 수명은 Flutter 담당이며 서버가 대신 완료했다고 보고하지 않는다. 같은 데이터의 생산자/저장소/소비자까지 살피고 무관 문제는 근거와 후속으로 분리한다.

기능/구간 종료 검증은 바뀐 위험에 맞춰 권한·위조/CAS·동시성·원자성·중복/원명령 재시도와 기존 정상흐름 보존을 확인한다. 테스트 개수만으로 품질을 선언하거나 동일 시험·정상 UI를 관성적으로 반복 요청하지 않는다. 정적 검토, mock, 격리 PostgreSQL, 실제 서버, 실회원/기기 근거와 미실행을 구별한다. 순수 문서 수정에는 서버/DB 재실행이나 코드 시험을 요구하지 않는다.

메모리/성능 개선은 실제 측정 조건과 전후 근거로만 주장한다. 종료 코드나 상한이 있다는 이유만으로 누수/성능 인수를 선언하지 않는다. 불필요한 요청·무제한 캐시를 방치하지 않되 추정 트래픽을 이유로 복잡한 캐시/이벤트 체계·과한 추상화를 선제 도입하지 않는다.

## 현재 적용 범위와 릴리즈 이후

이 기준은 이후 승인된 기능 작업의 선택·계약·검증·인계부터 적용한다. 기존 전체 코드의 감사/리팩토링·미확인 성능/누수 통과, API/DB/배포 변경을 뜻하지 않는다. Issue13의 기능·인수와 독립이며 사용자·데이터 보호/commit·push·merge·배포 승인 범위는 기존 규칙 그대로다.

우선은 Firebase 담당 기능의 Python Backend 대체, 필수 결함 해결·실회원/기기 인수와 서비스 가능한 릴리즈다. 그 배포와 안정 상태를 실제 확인한 종료 보고에서 배포된 main 커밋/태그 기준의 목적별 최적화 브랜치를 필요시 별도로 검토할 시점임을 사용자에게 안내한다. 그때 실제 main/dev·배포 태그 차이와 기존 통합 절차를 확인한다. 지금 최적화 브랜치·자동감시/예약·전면 리팩토링·조기 병합·배포/데이터 정리를 시작하지 않는다. 일반 기능의 기존 브랜치 규칙은 유지한다.
