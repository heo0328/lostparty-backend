# Issue 기반 Backend·Flutter 작업 단계와 진행 경계

사용자 확정 작업 기준: 2026-10-14. [API 협업](API_COLLABORATION.md)의 단계별 실행 기준이다. Backend GitHub Issue에서 Flutter Codex와 협업하며 각 단계의 결과를 다음 단계의 입력으로 사용한다.

작업 시작·인계 시 Issue 본문과 최신 댓글을 확인하고 [공통 협업 규칙](API_COLLABORATION.md#공통-협업-규칙)을 적용한다. 협업에 필요한 요청·인계와 받은 요청의 같은 Issue 결과 회신을 남기되, 변화 없는 상태나 독립 내부 작업에 댓글/테스트 요청을 일괄 요구하지 않는다.

## 기본 원칙

한 이슈는 한 주제/완료 조건을 다룬다. 직접 필요한 연계는 포함하되 독립 범위가 커지면 별도 이슈로 이관하고 원본 링크·담당·완료/대기를 보존한다. 현재 상태는 본문에 정리하고 변화 없는 진행 댓글/반복 명세로 스레드를 늘리지 않는다. 상세 기준과 현재 주제 목록은 [API 협업](API_COLLABORATION.md#이슈-범위와-마감)과 [이슈 추적표](project/ISSUE_TRACKER.md)를 따른다.


**합의된 API는 구현하고 Backend 검증을 수행한 뒤 Flutter가 테스트하도록 인계한다. 테스트 이후에 확인할 사실을 전체 구현의 선행 조건으로 두지 않는다.** 자료 요청은 해당 자료에 직접 의존하는 작업만 보류하는 근거이며 다른 구현·테스트를 멈추는 근거가 아니다.

실제 provider·기기 증거가 없어도 명시된 계약과 격리 DB·모의 adapter로 구현하고 검증할 수 있는 영역은 진행한다. 다만 mock 통과를 실연동 완료로 표시하거나, 증거가 필요한 실제 소유권 판정을 임의로 허용하지 않는다. 판단 근거가 부족한 정책은 영향 범위만 분리해 합의한다. 이미 수용된 항목은 다시 동의를 요구하지 않는다.

## 요청 → 답변 → API 작업 → Flutter 테스트 → Backend 후속 작업

| 단계 | 담당·수행 | 완료 산출물·다음 입력 |
|---|---|---|
| 1. 요청 | Flutter는 화면·사용자 동작·필요 데이터·보존/제외 범위를 Backend Issue로 요청한다. Backend는 요구와 기존 계약을 확인한다. | 관련 Issue, 필요한 기능과 이번 작업 범위 |
| 2. 답변·경계 합의 | Backend는 DTO·오류·권한·상태·버전·재전송 규칙을 제안한다. Flutter는 소비 가능 여부와 수정사항을 회신한다. 즉시 결정할 정책과 실행 후 확인할 사실을 구분한다. | 구현할 계약, 좁은 보류 조건, 실검증 항목·담당·시점 |
| 3. API 작업·Backend 검증 | Backend는 합의된 route·service·migration·OpenAPI와 의미 있는 테스트를 구현한다. 실제 key/기기가 없어도 adapter를 분리해 권한·경쟁·rollback·상태 전이를 검증한다. | 구현 결과, 자동 검증 증거, 실행 조건, 실제 연동에서 미확인인 항목 |
| 4. 인계·Flutter 테스트 | Backend는 검증된 작업 구간을 먼저 커밋·push하고 원격 반영을 확인한 뒤 사용할 계약·버전·접속/설정 조건·예제·한계를 인계하고 테스트·확인을 요청한다. Flutter는 해당 계약을 연결하고 전체 사용자 흐름·오류·재시작/재조회 등을 검증한다. 실제 외부 API가 필요한 흐름은 key/연결 준비 후 공동 테스트한다. | 소비한 계약 버전, 성공/실패 흐름, 오류code/request_id, 재현 조건, 미실행 원인 |
| 5. 테스트 후 Backend 작업 | Backend는 테스트 결과를 계약/구현 오류·provider 관찰·환경 문제·추가 정책으로 분류해 수정·재검증·인계한다. 변경된 흐름은 Flutter가 다시 확인한다. | 수정된 계약/구현·회귀 결과, 실연동 근거, 남은 제한과 후속 작업 |

단계는 기능 단위로 반복한다. 한 외부 연동이 대기 중이어도 다른 API의 구현·인계·Flutter 검증은 진행한다. 네이티브 테스트·확인 인계에 필요한 승인된 작업 구간의 작업 브랜치 commit·push는 사용자 상시 승인 규칙으로 먼저 수행한다. merge·PR·배포 및 별도 범위 게시에는 기존 승인 기준을 따른다. 게시 승인 전에도 로컬 구현·검증·검토 가능한 결과를 준비하며, 미게시 계약을 원격에서 사용할 수 있는 것으로 안내하지 않는다.

## 미확인 항목을 분류하는 기준

| 분류 | 판단 질문·예시 | 실행 기준 |
|---|---|---|
| 구현 전 결정 필요 | 답에 따라 공개 범위·소유권 정책·DTO 의미가 달라지는가? 대표 cooldown 예외, 타인 데이터 공개, 삭제/이전 정책 | 해당 정책의 계약과 동작만 보류하고 Issue에 대안·영향·답할 항목을 제시한다. 독립 영역은 진행한다. |
| 지금 구현·자동 검증 가능 | 합의된 입력/출력과 서버 불변식을 코드·DB로 검증할 수 있는가? 등록 CRUD, migration, UUID, 멱등, 버전, pagination, 대표/활동, 소유권 transaction | 바로 구현한다. 모의 provider로 경합·실패·rollback도 검증하고 실제 외부 자료는 후속 확인으로 기록한다. |
| 실제 provider 실행 시 확인 | 실제 응답 형태·quota·지연·장비 해제·누락 관찰이 필요한가? | adapter/상태 전이/실패 처리는 먼저 구현한다. key 준비 후 Backend가 실응답 근거를 확보한다. 실제 증거를 요구하는 판정 분기만 보류한다. |
| Flutter 테스트 이후 확인 | 화면 연결·요청 순서·페이지 수집·응답유실 UI·로컬 보존이 실행해 봐야 드러나는가? | 먼저 API와 테스트 가능한 계약을 인계한다. Flutter 테스트 결과로 재현·수정한다. 테스트해야 얻을 결과를 구현 전부터 요청하며 대기하지 않는다. |
| 별도 승인 필요 | 운영 변경·데이터 파괴 또는 승인되지 않은 게시인가? | 해당 실행만 승인 범위에 따라 보류한다. 코드/문서/격리 검증까지 준비한다. |

보류할 때는 `항목 / 필요한 결정 또는 증거 / 직접 막히는 동작 / 계속할 작업 / 확보 담당·시점 / 해제 조건`을 적는다. 단순히 “자료 부족으로 작업 대기”라고 기록하지 않는다. 필요한 외부 사실을 Backend가 직접 확인할 수 있으면 담당 작업으로 배정하고 Flutter에 같은 자료를 반복 요청하지 않는다.

## 자료 요청만 반복하지 않기 위한 실행 기준

1. 새 회신을 읽으면 수용된 정책을 계약에 반영하고 다음 구현 단위를 시작한다. 이미 답한 항목을 미합의로 남기지 않는다.
2. 질문을 보내기 전에 무엇이 실제로 막히는지 확인한다. 실provider key가 없다는 이유로 등록·DB 제약·멱등·활동 설정까지 보류하지 않는다.
3. 동일한 미확인 내용을 다시 요청할 때는 새로 드러난 모순이나 구체적인 검증 실패가 있어야 한다. 없으면 기존 후속 입력을 유지하고 가능한 작업을 실행한다.
4. 내부 구현 선택은 Backend가 정하고 검증한다. 계약 의미나 사용자 정책을 바꾸는 결정만 필요한 상대에게 요청한다. 질문 목록을 늘리는 것을 구현 진척으로 기록하지 않는다.
5. 단계를 끝낼 때 구현·테스트·인계 결과를 함께 기록한다. 요청/답변 수, 초안 작성, mock 성공만으로 기능 완료를 선언하지 않는다.

## Issue #3에 적용할 작업 분류

기준 회신: [Flutter A/B·경계 보완 수용](https://github.com/heo0328/lostparty-backend/issues/3#issuecomment-6159847616). 기존 답변과 함께 수용된 계약을 구현 기준으로 사용한다. provider 근거가 필요한 부분만 분리한다.

| 지금 Backend에서 구현·검증 | 실제 provider/Flutter 테스트 후 확인·수정 |
|---|---|
| 내 등록 조회·등록·수정·제거, additive migration·DB 제약 | 실제 siblings 필드/nullable/수치 표현·응답 상한을 adapter와 대조 |
| strict DTO·UUID·인증·본인 scope·등록/소유권/활동 상태 분리 | 실제 장비 해제 표현·API 갱신 지연·provider 장애/429/실quota 확인 |
| 전체settings와 pagination, 세 version/revision, stale 조회/저장 오류 | Flutter 전체 페이지 수집·혼합 draft 방지·409 후 명시적 재저장 확인 |
| 멱등 scope/hash·처리 lease/crash 복구·DELETE 성공 replay·응답유실 복구 | Flutter가 같은 key/payload를 보존하는지, challenge 현재 상태를 재조회하는지 확인 |
| challenge 시작/확인/취소/만료, canonical identity·소유권/이전/audit transaction과 경합·rollback | 실제 roster 감소/전체성의 허용 관찰 기준 합의와 live 이전 공동 인수 |
| 활동·대표 atomic save·최소1명·대표 포함·cooldown·재인증 설정 보존·소유 상실 | 실제 UI 상태·로컬 빌드/캐릭터 보존·재로그인/재조회 인수 |
| adapter 분리, quota/TTL·청소·오류·보류 상태, OpenAPI/자동 회귀 | 환경·접속·key 준비 후 실연동, 테스트 실패에 따른 parser·DTO/오류 보완 |

소유권 transaction과 missing/suspect 상태 처리는 모의 입력으로 먼저 구현·검증한다. live provider의 불완전 roster를 이용한 이전과 자동 missing 확정은 합의된 보류 조건으로 거절하며 증거 확보 전 성공 처리하지 않는다. 신규 자료가 필요한 경계 때문에 transaction 코드와 DB 경쟁 테스트까지 미루지 않는다.

## 인계와 후속 결과 기록

인계에는 무엇을 테스트할 수 있는지, 실제 provider 때문에 무엇을 아직 테스트할 수 없는지 명시한다. 모의 adapter 결과와 실제 API 결과를 구분한다. 실제 provider가 없으면 Backend 자동 검증을 먼저 완료하고 Flutter는 가능한 DTO/UI·오류 흐름을 검증하며, 실연동만 공동 준비 뒤 진행한다. mock을 실서버 proof로 받을 임시 공개 우회 API는 만들지 않는다.

- Issue: 합의·필요한 질문·구현/검증·인계와 Flutter 테스트 결과. 받은 요청의 결과는 같은 Issue에 회신한다. 구현/계약 SHA·브랜치·push 상태·계약 변경 내용을 필요한 만큼 기록한다. 테스트는 확인한 동작·통과/실패·미확인을 나누고 자동/mock·실제 서버/provider·사용자 결과를 구분한다. 실패는 흐름·기대/실제·계약 버전·안전한 오류code/request_id를 남긴다.
- NEXT_WORK: 다음에 실행할 구현 단위, 후속 담당·작업·완료 조건과 좁은 보류 항목·대기 사유를 관련 Issue/댓글 링크와 함께 기록한다. 실검증 준비를 모든 구현의 첫 단계로 두지 않는다.
- DEV_LOG: 실제 수행·결정·테스트 결과·미실행 원인. Backend 구현/자동 검증/실provider 검증/Flutter 적용/운영 완료를 별도로 기록한다.
- AI_CONTEXT: 기능 상태와 기준 문서 링크만 유지한다.

문서만 변경하는 단계에서는 문서 내용·링크·diff를 검증한다. 기능 구현 단계에서는 격리 PostgreSQL 및 API/OpenAPI에 맞는 검증을 수행한다. Issue 종료·운영 배포·기존 데이터 변경 권한은 협업 댓글이나 테스트 결과로 확대되지 않는다.
